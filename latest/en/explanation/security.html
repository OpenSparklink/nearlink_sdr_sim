Security Subsystem Details¶

This document explains the design and implementation of the SparkLink SLE security subsystem, covering pairing authentication, key derivation, frame encryption, privacy protection, and UWB measurement security, cross-referenced against Chapter 9 of TXS-10002-2025.

Security Architecture¶

The SLE security subsystem is organized in three layers:

  • Pairing authentication layer: establish trust relationships, exchange key material (§9.2)

  • Frame encryption layer: protect data transmission confidentiality and integrity (§9.3)

  • Privacy protection layer: prevent device tracking (§9.4)

Security is built on ECDH P-256 key agreement, from which all subsequent keys are derived.

Pairing Procedure (§9.2)¶

Pairing is the process by which two devices first establish a security association. The standard defines 6 authentication methods:

Method

Applicable Scenario

Numeric comparison

Both parties have display and input capability

Passkey entry

One party has input capability

Passkey verification

Pre-shared passkey

Out-of-band transfer

NFC and other side channels

Pre-shared key

Factory-provisioned key

No input

No interaction capability (Just Works)

The authentication method is determined by negotiating the IO capabilities of both parties (no input/no output, display only, keyboard only, display+keyboard, display+yes/no).

Pairing State Machine¶

The pairing procedure consists of 9 states:

        stateDiagram-v2
    [*] --> IDLE
    IDLE --> INITIATED
    INITIATED --> REQUEST_SENT
    REQUEST_SENT --> RESPONSE_SENT
    RESPONSE_SENT --> CONFIRM_SENT
    CONFIRM_SENT --> PUBLIC_KEY_EXCHANGED
    PUBLIC_KEY_EXCHANGED --> CONFIRM_CODE_SENT
    CONFIRM_CODE_SENT --> COMPLETED
    CONFIRM_CODE_SENT --> FAILED
    COMPLETED --> [*]
    FAILED --> [*]

G node perspective:

  1. IDLE → REQUEST_SENT: send PairingRequest, carrying IO capabilities, key length, security distribution info, encryption capability

  2. REQUEST_SENT → CONFIRM_SENT: received PairingResponse, sends PairingConfirm (containing G-node P-256 public key X/Y coordinates, 32 bytes each)

  3. CONFIRM_SENT → PUBLIC_KEY_EXCHANGED: received PairingInitialInfo (T-node public key), computes ECDH shared secret, sends Ra nonce

  4. PUBLIC_KEY_EXCHANGED → CONFIRM_CODE_SENT: received Rb, send GNodeConfirmCode

  5. CONFIRM_CODE_SENT → COMPLETED: received TNodeConfirmCode, verify confirmation code, derive keys

T node perspective is the mirror of the above procedure:

  1. IDLE → INITIATED: received PairingInitiate

  2. INITIATED → RESPONSE_SENT: received PairingRequest, send PairingResponse

  3. RESPONSE_SENT → PUBLIC_KEY_EXCHANGED: received PairingConfirm, saves G-node public key, sends its own public key

  4. PUBLIC_KEY_EXCHANGED → CONFIRM_CODE_SENT: received Ra, compute DH Key, send Rb

  5. CONFIRM_CODE_SENT → COMPLETED: received GNodeConfirmCode, verifies and sends TNodeConfirmCode, derives session keys

12 failure reasons:

Code

Reason

0x01

0x02

0x03

Authentication requirements not met

0x04

0x05

0x06

0x07

0x08

0x09

0x0A

0x0B

0x0C

Implementation: mac.security_manager.PairingManager implements the state machine; mac.security defines 20 pairing signaling message classes; mac.security_manager.ECDHKeyPair encapsulates P-256 elliptic curve operations.

Key Derivation (§9.3)¶

After pairing is complete, functional keys are derived step by step from the ECDH shared secret:

        flowchart TD
    DH["ECDH P-256 共享密钥 (32 字节)"]
    DH --> LK["Link Key (16 字节)\nKDF(dh_key_low128, 'lk' ‖ Ra ‖ Rb ‖ 地址)"]
    DH --> DK["DH Verify Key\nKDF(dh_key_low128, 'dk' ‖ Ra ‖ Rb ‖ 地址)"]
    DK --> DV["DH 验证码 (16 字节)"]
    DH --> SK["Session Key (16 字节)\nKDF(link_key, G_Diversifier ‖ T_Diversifier)"]
    SK --> AE["认证加密: SK 同时用于加密和完整性"]
    SK --> SEP["分离算法: EnK (加密) + InK (完整性)"]

KDF Algorithm¶

The standard supports two KDFs:

  • AES-CMAC: 128-bit key, 128-bit MAC output (§9.3.4)

  • HMAC-SM3: 256-bit digest, lower 128 bits used (§9.3.4)

Both parties negotiate which KDF to use during the pairing phase.

Confirmation Code Generation (§9.3.4.3)¶

The confirmation code ensures the remote device actually holds the DH Key. Generation depends on the authentication method:

  • Numeric comparison: KDF(PKax, PKax ‖ PKbx ‖ Ra ‖ 0)

  • Passkey entry: KDF(PKax, PKax ‖ PKbx ‖ Ra ‖ Ri)

  • Passkey verification: KDF(PKax, PKax ‖ PKbx ‖ Ra ‖ Pwd)

  • Out-of-band/Pre-shared/Just Works: similar to numeric comparison

Numeric Comparison Code (§9.3.4.6)¶

Take 4 bytes from KDF output, modulo \(10^6\), to get a 6-digit decimal number displayed to users on both sides for comparison.

Code implementation: the mac.crypto module implements all key derivation functions:

  • aes_cmac(), hmac_sm3(), kdf()

  • derive_link_key(), derive_session_key(), derive_dh_verify_key()

  • generate_confirm_code(), generate_dh_verify_code(), generate_numeric_code()

  • obfuscate() obfuscation algorithm (§9.3.4.7)

  • secure_random_256() secure random function (§6.10.7)

Frame Encryption (§9.3.1)¶

AES-CCM¶

SLE uses AES-CCM (Counter with CBC-MAC) for frame encryption, simultaneously ensuring confidentiality and integrity:

  • Confidentiality: AES-CTR mode encrypts payload

  • Integrity: CBC-MAC generates MIC (Message Integrity Code), 4/8/12/16 bytes in length

Nonce Construction¶

The nonce is a critical input to AES-CCM, ensuring each frame uses a different counter:

Asynchronous/synchronous unicast and multicast links:

┌───────┬──────────────────┬────────────┬─────────────┬──────────┐
│ Flag  │ payload_count    │ Direction  │     IV      │ data_len │
│ 1B    │ 5B (bit38:0)     │ 1b         │  8B         │ 2B       │
└───────┴──────────────────┴────────────┴─────────────┴──────────┘

  • payload_count: monotonically increasing counter (39 bits), prevents nonce reuse

  • Direction: 0 = G→T, 1 = T→G

  • IV: computed from the IV base value and frame parameters

Other links (broadcast/SMF):

┌───────┬──────────────────┬────────────┬─────────────┬──────────┐
│ Flag  │ slot_seq         │ day_count  │     IV      │ data_len │
│ 1B    │ 4B (bit29:0)     │ 2B(bit9:0) │  8B         │ 2B       │
└───────┴──────────────────┴────────────┴─────────────┴──────────┘

IV Computation (§9.3.1)¶

IV base value (8 bytes) XORed with different parameters:

  • FT1/FT2: IV = IV_base \(\oplus\) sync sequence number

  • FT3/FT4: IV = IV_base \(\oplus\) link ID

Implementation: mac.security_manager.FrameCryptoContext manages the encryption/decryption context, maintains TX/RX payload_count, and calls mac.crypto.aes_ccm_encrypt()/aes_ccm_decrypt().

Multicast Security (§9.3.2)¶

Multicast links use a separate key hierarchy:

RAND1, RAND2 (各 16 字节随机数)
    │
    └─► 组播密钥 GK = KDF(RAND1, RAND2)
            │
            └─► 组播会话密钥 GSK (16B)
                或 GEnK + GInK (各 16B)

Distribution procedure:

  1. G node generates RAND and KDF/encryption/integrity algorithm parameters, sent via MulticastAlgorithmConfig

  2. The G-node computes \(K_g\) = KDF(link_key, RAND) and sends \(C\) = \(K_g \oplus GK\) via MulticastKeyConfig

  3. The T-node computes \(K_g\) from its own link_key to recover \(GK\) = \(C \oplus K_g\)

Implementation: mac.crypto.generate_group_key(), derive_group_session_key(), derive_kg(); the mac.security module defines MulticastAlgorithmConfig and MulticastKeyConfig signaling messages.

Privacy Protection (§9.4)¶

SLE supports resolvable random addresses to prevent third-party device tracking:

  1. Device generates IRK (Identity Resolving Key, 16 bytes), exchanged during pairing via GNodeIRK/TNodeIRK

  2. Device uses IRK and a random number to generate a resolvable address (48 bits): upper 24 bits are hash(IRK, prand), lower 24 bits are prand

  3. Devices knowing the IRK can verify and resolve the address; devices without the IRK cannot correlate different addresses

Address distribution is accomplished through GNodeAddress/TNodeAddress signaling, carrying the address type (consortium-assigned, third-party local, consortium-reserved, private) and a 6-byte address.

Implementation: mac.crypto.generate_resolvable_address(kdf_type, irk, rand_part) and resolve_address(kdf_type, irk, addr).

UWB Measurement Security (§9.5)¶

UWB pulse measurement signals require dedicated security mechanisms to prevent distance spoofing attacks.

CTS Key System¶

Starting from the Link Key, derive UWB measurement-specific keys:

Link Key (16B)
    │
    └─► SLP Key = KDF(link_key, reserved ‖ "SLP" ‖ zeros)
            │
            ├─► ctsInitContent = KDF(SLP, "ctsInitC" ‖ inputContext)
            │       └─► ctsContent32Bit = ctsInitContent 低 32 位
            │
            ├─► ctsKey   = KDF(SLP, "ctsK"    ‖ ctsContent)
            ├─► ctsValue = KDF(SLP, "ctsV"    ‖ ctsContent)
            └─► ctsGap   = KDF(SLP, "ctsGapK" ‖ ctsContent)

inputContext (§9.5, Table 71)¶

128-bit context parameter encoding the physical layer configuration of the measurement session:

  • Physical channel number

  • Ranging method and mode

  • NMSS sample count

  • G node L2 ID

  • Antenna configuration

  • Other reserved bits

Key Update¶

After each measurement session, ctsContent32Bit is incremented and three keys are re-derived. This ensures each measurement uses a different scrambling sequence.

TGap Computation (§9.5.4)¶

TGap controls the time interval between CTS symbols, extracting 10 bits at an offset from the 128-bit ctsGap value:

\[T_{gap} = T_{base} - T_{offset}\]

where \(T_{offset}\) is computed from the corresponding bits of ctsGap.

CTS Symbol Generation (§9.5.5)¶

The CTS symbol sequence is used for time-domain scrambling of UWB measurement frames:

  1. For each symbol, ECB encryption with ctsKey generates a scrambling block

  2. Extract symbol index and SC value (+1 or -1)

  3. ctsVCounter incremented per symbol

Code implementation: phy.uwb_measurement_security module:

  • UWBMeasInputContext: 128-bit context encoding

  • CTSKeys: key set container

  • derive_slp_key(), derive_cts_keys(), update_cts_keys()

  • compute_tgap(): TGap time interval computation

  • generate_cts_symbols(): CTS symbol sequence generation
